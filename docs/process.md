# Feature 开发流程

本项目以学习 Agent 开发为目的。每个功能（主题）都按六个阶段推进，**用户全程参与讨论并在关卡处明确确认**。流程的价值在于"想清楚再做"和"做完能讲清楚"，而不是交付速度。

## 总览

```
① 需求定义 ──G1──▶ ② 业界调研 ──G2──▶ ③ 技术方案 ──G3──▶ ④ 实现 ──▶ ⑤ 验证与评测 ──▶ ⑥ 学习总结
```

| 阶段 | 目标 | AI 职责 | 用户职责 | 产出（写入主题文档对应章节） |
| --- | --- | --- | --- | --- |
| ① 需求定义 | 讲清楚要解决什么问题、不做什么 | 提问、补全场景、指出模糊点 | 定义目标与边界 | 背景、目标、非目标、用户场景、验收标准 |
| ② 业界调研 | 了解优秀 Agent 如何解决同一问题 | 阅读源码与文档，形成对比 | 追问、挑选值得学习的点 | 对比表、关键设计、引用链接、启发 |
| ③ 技术方案 | 在备选方案中做出有依据的选择 | 提出 2～3 个方案并分析取舍 | 拍板 | 备选方案、决策（ADR）、模块与接口、测试计划、拆分的 PR 列表 |
| ④ 实现 | 按方案交付 | 小步编码，配测试，开 PR | 评审 PR | 代码、测试、文档更新 |
| ⑤ 验证与评测 | 证明它真的工作 | 运行测试/评测，如实记录 | 实际试用确认 | 验证记录（通过、未验证、已知限制） |
| ⑥ 学习总结 | 把经验沉淀为自己的知识 | 提供骨架、素材、与调研对象的差距 | **执笔** | 核心概念、踩坑、与业界差距、后续问题 |

## 关卡规则

- **G1（需求确认）**：验收标准可检验，非目标已写明。
- **G2（调研讨论）**：至少对比 2 个参考实现；用户已就"借鉴什么、不借鉴什么"给出意见。
- **G3（方案确认）**：决策与取舍已写明，测试计划和 PR 拆分已列出。**G3 之前不得修改代码。**
- 关卡确认记录在主题文档的「关卡记录」表中：日期、结论、确认人。
- 实现中若发现方案需要实质性变化，回到 ③ 重新讨论并更新文档，而不是边写边改。
- 小 Bug 修复与纯文档修改可以走简化流程：讨论原因与方案 → 用户确认 → 修复（附回归测试）。

## 调研要求

- 每个主题选 2～4 个参考对象，优先**开源且有源码可读**的项目（如 OpenAI Codex CLI、Cline、smolagents、OpenAI Agents SDK、Letta），辅以官方工程文章（如 Anthropic、Manus 的公开文章）。
- 每条结论附**源码文件路径/提交或文档链接**；记录查阅日期。闭源产品只能引用官方文档或公开文章，其余标注「推测」。
- 关注"为什么这样设计"，而不只是"怎么写"：它解决了什么问题，代价是什么，是否适合本项目的规模。
- 输出一张对比表 + 本项目的启发（借鉴/不借鉴/暂缓）。

## 实现要求

- 一个主题对应一个 GitHub Issue（或里程碑），实现拆成多个小 PR，每个 PR 在描述中链接主题文档。
- 分支命名：`feat/<编号>-<短名>`，例如 `feat/s1-agent-loop`。
- 每个 PR：代码 + 测试 + 文档同步；CI 通过后合入。
- 详见 [conventions.md](conventions.md) 与 [testing.md](testing.md)。

## 学习总结要求

- 写在主题文档的「⑥ 学习总结」章节，由用户执笔。
- 建议回答：这个能力的本质是什么？业界方案的共性与差异？我们的实现做了哪些简化？踩了什么坑？如果做到工业级还差什么？
- 完成后在 [learning/README.md](learning/README.md) 的索引中登记。

## 与 AI 协作的建议

- 每次会话开始告诉 AI 当前主题与阶段，例如「继续 S1，阶段 ② 调研 Codex 的 agent loop」。
- 在阶段 ②③，多问"为什么"和"如果不这样会怎样"；让 AI 给出反例与失败场景。
- Codex 与 Claude Code 共用 `AGENTS.md`；可以让一个工具实现、另一个工具评审，获得独立视角。
